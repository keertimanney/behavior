Research and design recommendations · Robot Learning Collective · 5 November 2026

Make Astra’s task-solving trace inspectable

Recommended direction: combine a chaptered robot replay, an observation–action–result inspector, and a compact timing overview. Use a small evidence graph only for selected moments. Preserve the distinction between recorded agent inputs, returned summaries, analyst interpretation, and evaluator-only state.

This report is research, not a prototype implementation. Episode facts below come from the supplied task brief; I did not independently audit the underlying episode files. Public sources were checked through papers, official documentation, repository files, and separate browser tabs. PAIR’s trace demo and AgentPrism’s Storybook were visually inspected. Laminar’s synchronization is documented and demonstrated in public material; I did not test it in a customer account.

Useful secondary references

  • AgentPrism: public Storybook, code, and design article. Visually verified a three-pane trace list/tree/details view, duration bars, and error drill-down. Good inspiration for the expandable technical inspector. The README calls the library alpha and requires React/Tailwind; use the pattern rather than the package. Do not adopt its promotional “perfect information” claim.
  • Perfetto: timestamped data conversion and track events and flows. Borrow duration slices and selection-only dependency arrows. Draw cross-lane arrows only when request IDs or explicit references support them. A chronological neighbor is not necessarily a dependency.
  • Graph of Trace, ACL 2026 demo: paper and code/demo. Implemented live DAG with artifact links. Its framework uses an LLM to extract graph nodes from reported subtasks and artifacts; this is a derived representation. Borrow artifact-backed provenance and parallel sibling nodes, but preserve the original log and record how any semantic graph was produced.
  • Inspect View: official viewer documentation separates message histories, scoring decisions, and metadata, and documents static bundles for GitHub Pages or bucket hosting. Useful publishing precedent. mini-SWE-agent’s trajectory browser is an even closer implementation reference: Hugo and JavaScript, JSON traces, responsive reading, and deep links. Neither requires Astra to adopt its schema.
  • IBM Agent Trajectory Explorer (AAAI 2025): official publication. A demonstrated visualization/annotation tool. The publisher’s full-paper endpoint was blocked during this review, so I have not used it as evidence for specific UI behaviors.

Recommended layout for the supplied Astra episode

Start with the task, final outcome, and one sentence explaining the replay. The supplied record has 90 model requests, 102 tool calls, 14 returned reasoning summaries, about 92.97 seconds of simulation video, and about 1816.8 seconds of wall time (30 min 16.8 sec). Keep the two durations visible. Model requests and tool calls may nest or overlap; their counts do not imply 192 sequential, mutually exclusive steps.

On narrow screens: video, selected event, then overview. Provide previous/next event buttons and chapter links; essential evidence cannot require hover. Keep arbitrary payloads collapsed and human-readable arguments visible.

Chaptering and selection

Choose roughly five to seven chapters after reviewing the episode, using changes of subgoal or strategy rather than equal time intervals. Candidate categories are initial inspection, approach, manipulation, verification, and recovery. These are a proposed vocabulary, not assertions that each occurred in this run. Label authored summaries as editorial annotations; retain the original action text and event IDs.

Select a chapter to set a bounded replay interval and list its events. Select an event to show the input image actually sent to the model, the action, and its returned result. If only a later image exists, label it “next recorded observation” with its timestamp and delay. A spectator-camera video is useful context but should not be labeled the model’s visual input unless verified.

Two clocks without false precision

  • Default playback follows the simulation video; the wall-time cursor follows recorded alignment anchors. A wall-time view can expose model latency, tool waits, and concurrency.
  • Do not multiply all video timestamps by the ratio of the two total durations. Simulation can pause while wall time advances, and several calls can map to the same simulation frame.
  • When the mapping is many-to-one, show the relevant wall-time interval or stack of events. If an exact mapping is unavailable, show “nearest recorded anchor” or an uncertainty interval; do not interpolate a robot state across an unobserved gap.
  • Label any compressed idle gaps and retain their real duration. Changing playback speed or compressing display space must not change reported timings. Empty intervals mean “no logged event,” unless the record actually establishes waiting or inactivity.

Provenance, uncertainty, and the final call

Give every displayed statement one origin: agent input, tool output, returned reasoning summary, editorial annotation, or evaluator-only evidence. The 14 summaries do not establish that every request has a visible explanation. A missing summary means “not returned/available,” not “no reasoning.” Do not generate replacement inner narration.

Use categorical evidence labels and explicit unknowns. A confidence meter is appropriate only if the run recorded a quantity with a defined meaning; do not infer numerical confidence from fluent text, repeated actions, or a successful outcome. Record alignment quality separately from task success and from any model-supplied confidence.

Final annotation: “Evaluator reports task success. The final robot call is recorded as error/interrupted.” Display these as separate facts with separate source links. The supplied brief does not establish why the call was interrupted or the precise causal relationship between interruption and success.

Keep evaluator grasp/goal state below a divider with “Not supplied to the agent” where confirmed. Do not draw it as an input into Astra’s decision loop. This prevents a reader from attributing privileged feedback to the agent.

Retries, branches, and multiple agents

A retry remains on the chronological timeline as attempt 2, 3, and so on. Highlight changed arguments and the intervening feedback. Repeating a tool name alone is not sufficient to call it a failed retry: the same tool may act on another object or viewpoint. A branch diagram requires separately recorded continuations from a shared point; distinguish hypothetical alternatives from executed ones.

Keep model/tool/robot/context as activity lanes. They are not four agents. If future logs contain real subagent identities, add nested lanes using parent IDs and message/handoff links; overlapping spans should remain visibly parallel. Show an edge only for a recorded dependency, or explicitly mark it as an analyst hypothesis.

Three diagram concepts for the paper and blog

1. Evidence-backed task sequence — primary paper figure

A two-column-width filmstrip with four to six selected moments. Each column contains an actual observation or clearly labeled spectator frame, the issued action, and the recorded result. Put a short returned summary beneath only those moments that have one. A thin separate bottom strip shows evaluator-only goal evidence. Cite exact event IDs and both available timestamps in the caption or supplementary table.

Question answered: What changed in the environment, and what did Astra do next? Borrow the legible skill/frame structure from SayCan and the feedback sequence from Inner Monologue. Use a numbered timeline for execution order; avoid a long curved arrow implying an unobserved mental process. Caption template: “Selected recorded observations, actions, and results from one episode. Evaluator state is shown separately and was not an agent input. Summaries are partial returned records.”

2. One episode, two clocks — timing figure

Top panel: simulation-time filmstrip spanning approximately 0–92.97 s. Bottom panel: wall-time lanes spanning approximately 0–1816.8 s. Match a small number of verified anchor events with the same symbols in both panels. Use connecting guides between anchors, not a shared axis. Shade an interval only when its meaning is supported by logged durations; use a visible break symbol if a detail inset compresses time.

Question answered: How does visible robot progress relate to computation and tool execution? Add the two durations directly to their axes. Do not label their ratio as real-time speed or subtract video duration from wall time to claim model latency: those inferences require more measurements.

3. Recovery evidence, or outcome/status separation — explanatory inset

If a verified recovery exists, show three successive attempts with the changed parameter highlighted, returned feedback beneath, and arrows labeled “next recorded action.” If no convincing recovery is present, use the known final distinction: final robot action → recorded tool status “error/interrupted”; a separate evaluator evidence path → “task success.” The two paths can share the episode boundary without a causal arrow between interruption and success.

Question answered: Which evidence supports the interpretation? Adapt TraceView’s local inspection and AGDebugger’s aligned alternatives only where the record supports them. A short evidence chain is more defensible and printable than a full graph of every event. A blog click on any figure panel should open the same event in the replay.

Lightweight publication recommendations

Use the existing HTML/CSS/JavaScript viewer, a compact JSON event manifest, native video, and an SVG overview. Precompute reviewed chapter labels and alignment anchors locally. Keep media in the bucket and load the selected observation on demand. Use durable publication URLs and avoid embedding expiring signed URLs in the paper or blog.

Give events stable permalinks such as #event=<stable-id>; maintain one selection state across replay, inspector, and timeline. Preserve source identifiers and retain the original record for audit. A small manifest can carry wall-time bounds, simulation anchors, observation references, tool request/result IDs, evidence origin, and editorial annotation provenance. Verify CORS, video seeking/range behavior, and page refresh on an event link in the actual hosting setup before publishing.

Prioritize now: reviewed chapters, honest two-clock mapping, observation/action/result inspection, provenance labels, and the final status/outcome annotation. Add full graph navigation, multi-run comparisons, or semantic search only when there is a concrete reader question and sufficient data.

Research limitations: no benchmarking of the tools, no full reproduction of their experiments, and no independent validation of Astra’s event counts or alignment. Public source interfaces can change. Recommendations are this report’s synthesis, not claims made by the cited authors.
